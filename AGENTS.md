# mcpwarden agent notes

This repository contains a headless Go MCP gateway and a separate admin UI in `ui/`. Compose runs them as separate services. The UI reads status and tool metadata from the gateway HTTP API. Keep the two components separate.

## Scope

V1 proxies MCP tools from stdio and Streamable HTTP upstreams. It supports namespacing, dynamic tool refresh, allow/deny policy, static operator bearer auth in local mode, optional OAuth resource-server auth for ChatGPT MCP connections, an approval interface with a `None` implementation, and indexed call history. Users can register their own remote MCP endpoints and credential header names through the UI. These registrations, the last successful tool discovery, accounts, access records and history are stored in the required database (SQLite by default, or PostgreSQL), with secret-bearing fields sealed under the catalog key. When OAuth mode is enabled, the validated token subject selects each user's upstreams and the admin API requires a separate management scope. The external identity provider owns OAuth login and token issuance. Basic local panel registration was authorized by the user on 2026-09-21: encrypted account storage, password hashing, browser sessions, and per-account opaque MCP tokens are now in scope. Local accounts and external OAuth are mutually exclusive; accounts are personal workspaces, not global administrator roles. Do not add an embedded authorization server, push approvals, resources, prompts, databases, without discussing the scope first. The user explicitly authorized separate admin/client MCP views, per-provider refresh for both, admin provider-management tools, named revocable API keys and sessions, hard active limits, and lifecycle timestamps on 2026-09-21.

Upstream authentication was explicitly expanded by the user on 2026-09-21: no auth, bearer/API-key/custom headers, and generic MCP upstream OAuth consent. Credentialed personal connectors are now vault-only from creation: the catalog stores header names only, the credential lives in the owner vault, and calls need an owner-activated access window. Upstream OAuth for personal connectors is removed and returns under the vault in roadmap step 6. Catalogs from older builds are refused, not converted. A built-in Google Drive API adapter is not included; the user has not selected a Drive MCP server.

Per-user tool-call history, history filters, metadata-only responses, and local password changes were authorized on 2026-09-21. Audit history is append-only, owner-scoped, and linked to stable tool IDs with name snapshots. Connector deletion must retain historical call records.

The user requested review and implementation of the timed-access security spec v1.1 on 2026-09-22, then explicitly authorized PostgreSQL test infrastructure and migration design. The staged roadmap and exact current coverage are in `docs/security/implementation.md`; the original bundle is in `docs/security/spec-v1.1/`. Public caller IDs and durable dispatch audit are integrated. The lease engine, the metadata stores, real envelope activator and guarded proxy adapter have end-to-end SDK tests on SQLite and PostgreSQL. Startup installs that adapter whenever `owner_security` runs; without it only no-auth personal connectors can be created. The live deployment does not run `owner_security`, so do not claim browser vaults or production lease enforcement is enabled there. See `docs/security/encrypted-runtime.md` for the exact boundary and remaining gates. Vault custody requires a distinct interactive owner flow even when extra approval is `none`; ordinary admin MCP keys cannot self-activate. Push and TOTP remain optional and unselected.

On 2026-09-25 the user decided there is no legacy: the project is not really live, so there is no backward compatibility and no live migration; deployments start fresh. Storage is required and is SQLite (the default) or PostgreSQL, configured in the `storage` section; see `docs/storage.md`. The file catalog, JSONL history and the import, cutover and rollback tooling are removed, and removed configuration keys and pre-reset databases are refused, never converted. SQLite was authorized as part of the approved removal plan (2026-09-26); other databases still need discussion. Storage failures never fall back, and caller cancellation is not a storage failure. Every catalog change commits with its security event and any lease revocation in one owner transaction, and publishes after commit. Both schemas start from one baseline; every later change is a numbered migration on both dialects, and a baseline is never edited. `--stdio` needs SQLite: it shares the database with other stdio clients, never with a running gateway, and writes only history. The approved plan is `/mnt/project-files/plans/remove-legacy-plan.md` when that shared folder exists.

Browser vault worker primitives use pinned hash-wasm Argon2id, exact root/CEK wrappers and recovery interoperability tests. PostgreSQL stores ciphertext records with CAS, nonce uniqueness, write caps and tombstones. Schema v3 adds the opt-in owner security API and approval policy storage; see `docs/security/owner-api.md`. `Service.ChangeOwnerAtomic` rechecks interactive browser authority and coordinates ciphertext writes, lease revocation and post-commit cache publication. Browser revocation and password changes share that owner gate. The API requires verified TLS or an explicitly trusted proxy; loopback HTTP development is a separate opt-in. In Compose, `compose.tls.yaml` adds HTTPS through the pinned ui proxy. The opt-in Vault & windows console now provides setup, unlock, credential entry and explicit access-window flows. Guarded execution runs whenever `owner_security` is set, and live `owner_security` stays disabled. The user owns deploys and redeploys after a validated batch; take a consistent protected backup before redeploying. The next deployment is a fresh start: the old volume is kept untouched as the backup.

## Code and validation

- Use the official `github.com/modelcontextprotocol/go-sdk` and verify API details in the pinned module source before changing SDK calls.
- Keep `examples/config.yaml` in sync with `internal/config`.
- Do not log raw tool arguments, results, or credential values. Audit stores only a canonical argument hash.
- Preserve argument-hash bytes independently from future RFC 8785 approval hashes. A successful dispatch-admission write must be durable before any tool execution; completion failure must never cause tool replay or replace a successful result with a claimed failure.
- Keep personal upstreams, headers, cached tools, and admin API responses scoped to the validated user. Never expose stored header values in API responses.
- Keep hidden tools in the admin inventory so users can re-enable them, while excluding them from MCP `tools/list` and denying direct calls.
- Add dependencies only when justified. PostgreSQL uses pinned pgx, SQLite uses pure-Go `modernc.org/sqlite`, approval hashes use an RFC 8785 implementation, and the user selected Sonic for JSON performance. Keep legacy argument-hash serialization unchanged. Sonic is configured centrally in `internal/jsoncodec`; no `GOEXPERIMENT=jsonv2` is required.
- Read the package and its tests before editing. Keep changes focused and use `gofmt`.
- Before a milestone is done, run `go build ./...`, `go vet ./...`, and `go test -race ./...`; record the result in `docs/progress.md`.
- Record decisions involving SDK or MCP behavior in `docs/decisions.md`.
- Do not add AI attribution anywhere: no `Co-Authored-By` or `Claude-Session` commit trailers, no "Generated with Claude Code" lines or claude.ai session links in commits, pull request descriptions, documentation or code comments. The commit author name "Claude" is fine.
